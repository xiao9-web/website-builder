# 阿里云上线检查

此目录提供部署模板，没有修改线上服务器。目标服务器为上海 ECS，2 核 / 2 GiB。正式部署时将模板中的 `SERVER_PUBLIC_IP` 替换为实际公网 IP；目标是域名访问公司官网、直接访问 IP 查看个人博客。

## 上线前仍需完成

- 确认公司法定名称、公开联系方式、产品资料及图片授权；替换演示内容，清除未确认的承诺与参数。
- 完成适用的 ICP 备案。此前访问 `www.chunchang.tech` 看到阿里云备案拦截页，不能将本地试用称为公网已上线。
- 确认现有 Nginx / 博客配置、进程、监听地址、备份及恢复方法。安全组中 `8090` 的备注是个人博客，但本次尚未验证该端口实际运行的服务。
- 确认博客在代理后的 `Host`、外部 URL 和资源路径均正常；不要直接覆盖其现有配置。
- 目前 DNS 只有 `www` 的 A 记录指向服务器；新增根域名 `@` 的 A 记录需在变更前核实。
- 安全组当前没有 `443` 入站规则；申请包含根域名与 `www` 的 TLS 证书并开放 `443`。公司后台仅通过 HTTPS 对外提供。
- 测量官网与博客同时运行的内存占用。历史快照显示 ECS 内存已使用约 66%，尚未证明新应用在这台机器上能稳定共存。
- 用公司确认的 MP4 测试首页视频：上传限制 30 MB，代理请求体限制 32 MB；确认点击前没有视频请求，点击后可播放并用 HTTP Range 拖动。现有公网带宽约 3 Mbps，须在真实手机网络测试加载速度，必要时压缩视频。

## 最小部署方法

1. 在隔离目录安装锁文件中的依赖并构建；推荐在有足够内存的构建机器完成。不要在 2 GiB 服务器上直接假设构建一定成功。
2. 用专用系统用户 `chunchang` 运行应用；代码放在 `/opt/chunchang/current`，数据放在 `/var/lib/chunchang`，环境文件放在 `/etc/chunchang/site.env`。持久化目录和环境文件不要进入 Git 或公开下载包。
3. 将 `.env.example` 对应变量填入环境文件：`DATABASE_URL=file:/var/lib/chunchang/content.sqlite`、`MEDIA_DIR=/var/lib/chunchang/media`、`SITE_URL=https://www.chunchang.tech`、`COOKIE_SECURE=true`。只有使用本模板并确保代理覆盖客户端 IP 请求头时才设置 `TRUST_PROXY_IP=true`。秘密值须由管理员生成；确认内容后才将 `DEMO_MODE` 改为 `false`。环境文件权限 `600`，由服务用户可读。
4. 安装依赖、完成构建、建立初始管理员并确认登录之后，将 `chunchang.service` 的 Node 路径与实际安装一致；提前创建 `.next/cache`、数据库和媒体目录，并赋予服务用户所需权限。
5. 验证公司应用只监听 `127.0.0.1:3001`；不要将应用端口、数据库或后台测试端口开放给公网。
6. 备份现有代理配置，再根据实际博客端口与证书位置调整 `nginx.conf`。运行 `nginx -t` 成功后才 reload；不要覆盖现有博客 server 块造成重复 `default_server`。
7. 验证下面的路由和后台操作，再切换域名与正式内容。

服务模板使用常规 `next start`，需要 `.next`、`node_modules`、`public`、配置和必要源码。这不是 Next standalone 包。应用代码与 SQLite / 上传目录分开保存，更新代码不能删除数据目录。

在发布目录中执行初始化和构建时，显式读取外部环境文件。以下命令应以有权限读取环境文件及写入数据目录的服务用户执行：

```sh
NODE_ENV=production node --env-file=/etc/chunchang/site.env node_modules/payload/bin.js migrate
NODE_ENV=production node --env-file=/etc/chunchang/site.env --import tsx scripts/bootstrap.ts
NODE_ENV=production node --env-file=/etc/chunchang/site.env node_modules/next/dist/bin/next build
```

先迁移、再建立管理员，最后启动服务。初始部署不要生成新的迁移，不要使用清空数据库的命令。完成首次账号创建后可从环境文件移除 `ADMIN_PASSWORD` 与 `ADMIN_EMAIL`；后台登录账号已经存储在数据库中。密码与固定的 `PAYLOAD_SECRET` 要独立保管；随意更换秘密会使既有登录会话失效。

## 实际服务器验收

```sh
curl -I http://SERVER_PUBLIC_IP/
curl -I http://www.chunchang.tech/
curl -I https://www.chunchang.tech/
curl -I https://chunchang.tech/
curl -I https://www.chunchang.tech/admin
```

预期：IP 返回博客；两个公司域名的 HTTP 转至 HTTPS；根域名 HTTPS 转至 `www`；公司首页可访问；后台要求登录。使用浏览器实际检查博客文章、公司产品、三级内容菜单与各级文章、有图/无图正文、图片轮播、点击后才加载的首页视频、询盘提交与后台查看，不能仅凭 `200` 状态码判定交付完成。未经登录不得读取询盘。

此环境未安装 Nginx，本次没有运行 `nginx -t`；以上是待验证的生产模板。TLS 证书、备案、DNS、安全组和服务器内存尚未验收。

## 备份与回滚

备份前安排短暂维护窗口，停止公司服务，保持数据库和上传文件在同一静止状态。以下示例只复制网站数据，不导出环境秘密：

```sh
sudo systemctl stop chunchang
sudo install -d -m 700 /var/backups/chunchang/manual
sudo sqlite3 /var/lib/chunchang/content.sqlite '.backup /var/backups/chunchang/manual/content.sqlite'
sudo tar -C /var/lib/chunchang -czf /var/backups/chunchang/manual/media.tar.gz media
sudo sqlite3 /var/backups/chunchang/manual/content.sqlite 'PRAGMA integrity_check;'
sudo systemctl start chunchang
```

使用每次不同的备份目录，避免覆盖上一次备份。数据库检查应返回 `ok`；备份后检查服务已恢复。将备份复制到另外的受控存储，并做一次隔离恢复测试；数据库和媒体必须一起恢复。只保留服务器本机副本不能覆盖服务器丢失风险。

代码回滚时恢复上一版发布目录和之前的 Nginx 配置；如果新版本已更改数据库结构，先在隔离环境验证旧代码与数据库兼容性，必要时恢复配套数据库和媒体备份。不要将恢复未经验证的旧数据覆盖当前生产数据。
